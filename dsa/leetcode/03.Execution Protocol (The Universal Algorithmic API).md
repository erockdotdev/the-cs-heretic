## Core Premise

Every problem is a negotiation among four currencies, under a fixed data topology:

1. **Time** (CPU cycles)
2. **Space** (memory)
3. **Order** (sortedness / monotonicity / predictability)
4. **Integrity** (original indices, exact history, path reconstruction)

You can never get something for free. Want $O(1)$ lookups? Pay the Space tax (a hash map ledger). Want $O(1)$ space? Pay the Order and Integrity tax (sort the array, which destroys original positions).

The interviewer never "tricks" you — they shut down one currency and force you onto the next legal architecture in the failure-driven chain. Your job is not to guess the algorithm name. Your job is to read the topology, audit the budget, identify the algebraic properties you can exploit, select the cheapest legal mechanism, and fail over cleanly when an assumption breaks.

## The Complete API Signature

```typescript
function solve(problem: LeetCodeProblem): Solution {
  const topology   = identifyTopology(problem.dataShape);              // Step 1
  const budget     = auditConstraints(problem.N, problem.extraConstraints); // Step 1
  const algebra    = probeAlgebra(problem.properties);                 // Step 2
  const family     = routeToFamily(topology, budget, algebra);         // Step 3
  const mechanism  = selectMechanism(family, algebra);                 // Step 3
  const exploits   = applyExploits(mechanism, problem);                // Step 4
  return executeWithFailover(mechanism, family, exploits);             // Step 4
}
```

## Step 1 — Input Handshake (Topology + Budget)

**Never read the story first. Read the shape and the numbers.**

**Topological Router (Primary Key)**

| Physical arrangement in memory          | Routes to                           |
| --------------------------------------- | ----------------------------------- |
| Contiguous array / string / stream      | **Family 1** — Linear               |
| Sorted values or overlapping intervals  | **Family 2** — Sorted / Ranges      |
| Nodes + edges (tree, graph, grid)       | **Family 3** — Network              |
| Continuously mutating or streaming data | **Family 4** — Priority / Streaming |
| Exponential sequences of decisions      | **Family 5** — State-Space          |

**Complexity Budget (Hard Constraint)**

See **04 — Formulas & Heuristics, §2** for the canonical N-scale table. Extra constraints ("$O(1)$ space", "negatives allowed", "return original indices") are **currency shutdowns** — they force you onto a different link in the failure chain (see Newly Formalized Concepts, below).

## Step 2 — Algebraic Probe (What can I exploit?)

Ask three binary questions:

1. **Is there order or monotonicity?**
   Yes → Binary Search, Two Pointers, Sliding Window, Greedy possible.
   No → Hash maps, graphs, or exhaustive search required.

2. **Are there overlapping subproblems + optimal substructure?**
   Yes → Dynamic Programming.
   No → Independent traversal or pure backtracking.

3. **Does data arrive or change while queries happen?**
   Yes → Heaps, Tries, monotonic deques, Fenwick/Segment trees.
   No → Static processing is enough.

These three answers, together with topology and budget, almost always select a unique mechanism inside the correct Super-Family.

## Step 3 — Route & Select Mechanism

| Topology + Algebra                           | Primary Mechanism               | Family |
| -------------------------------------------- | ------------------------------- | ------ |
| Contiguous + monotonic constraint            | Frame (Sliding Window)          | 1      |
| Contiguous + historical sums / "seen before" | Ledger (Prefix + Map)           | 1      |
| Sorted + pair / partition                    | Vise (Two Pointers)             | 1      |
| Sorted space or monotonic answer             | Pivot / Binary Search on Answer | 2      |
| Overlapping intervals / coverage             | Sweep Line                      | 2      |
| Tree / Graph / Grid, unweighted              | DFS / BFS + visited             | 3      |
| Dynamic connectivity                         | Union-Find                      | 3      |
| Continuous min/max or Top-K                  | Binary Heap / Monotonic Deque   | 4      |
| Heavy prefix sharing on strings              | Trie                            | 4      |
| Proven local → global                        | Greedy                          | 5      |
| Small $n$ or all solutions needed            | Backtracking                    | 5      |
| Overlapping subproblems                      | DP (state tuple design)         | 5      |

## Step 4 — Failure-Driven Execution & Cross-Family Exit

Every mechanism carries explicit assumptions. When an assumption is violated, do not invent a patch — follow the chain.

```
Family 1
  Frame  → loses monotonicity / negatives (Silent Failure risk)  → Ledger        ← pay Space Tax
  Ledger → O(1) space forced                                     → Vise          ← pay Integrity Tax (sort)
  Vise   → original indices required                             → back to Ledger

Family 2
  Classic BS → rotated                              → find pivot + BS
  Exact target → answer is the search space         → BS on Answer (feasibility often calls F1 or F5)
  Ranges → overlapping                               → Event Collapse → Sweep Line (± heap embedding)

Family 3
  Tree → cycles appear                              → Graph + visited / coloring
  Unweighted → weighted                              → Family 4 (Dijkstra embedding)
  Connectivity under merges                          → Union-Find (amortized potential)
  Count paths / heavy constraints                     → Family 5

Family 4
  Heap / Deque → need full order statistics          → Fenwick / Segment / Balanced BST
  Window extremes                                     → prefer Monotonic Deque over Heap
  (Most often used as an embedding inside 1–3)

Family 5
  Greedy → cannot prove exchange / matroid (Silent Failure risk) → Backtracking
  Backtracking → overlapping subproblems + large n                → DP (State Compression + Minimal Tuple)
  n ≤ 20 + subsets                                                 → Bitmask DP
```

**Most common Cross-Family Exits**
- Family 1 window needs current max/min → embed Family 4 deque/heap
- Family 2 feasibility check is itself hard → call Family 1 or 5
- Family 3 weighted edges → Family 4 Dijkstra
- Family 3 "count all paths" → Family 5
- Any topology + combinatorial explosion → Family 5
- 2-D version of a 1-D pattern → stay in Family 1 via dimensional collapse

## Newly Formalized Concepts

These give first-class names to ideas that were previously only implicit. Two of them (**Space Tax**, **Dimensional Collapse**) are already defined in 02 — Taxonomy §1 — they're listed here only for completeness; that doc is their canonical home.

| Concept                  | Definition                                                             | Role in the API                                  |
| ------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------ |
| **Currency Shutdown**    | An explicit constraint that forbids one of the four currencies         | Forces a specific link in the failure chain      |
| **Space Tax**            | *(see 02 — Taxonomy)*                                                  | Ledger, DP tables, visited sets, heaps           |
| **Integrity Tax**        | Destruction of original indices or path history (usually via sorting)  | Vise, some greedy sorts                          |
| **Dimensional Collapse** | *(see 02 — Taxonomy)*                                                  | 2-D → 1-D (rows as elements), tree → path, etc.  |
| **State Compression**    | Collapsing many histories into one equivalence class                   | DP memo keys, bitmask, prefix sums, visited sets |
| **Amortized Potential**  | The hidden "credit" that makes two-pointer / deque / Union-Find $O(n)$ | Frame, Monotonic Deque, Union-Find               |
| **Silent Failure**       | A technique that produces a wrong answer without crashing              | Greedy without proof, pure Frame on negatives    |
| **Assumption Surface**   | The exact set of conditions a mechanism requires to be correct         | The trigger for every failure-driven transition  |

## Newly Formalized Exploits (High-Leverage, Rarely Named)

The "black-magic" moves experienced solvers use, made explicit.

**1. Duality Exploits**
- **Ledger ↔ Vise Duality** — Need history + original indices → pay Space Tax (Ledger). Allowed to destroy history → pay Integrity Tax and buy $O(1)$ space (Vise after sort).
- **Greedy ↔ DP Duality** — Can prove local choice is safe → Greedy (extreme confidence). Cannot prove it → DP (extreme humility — store every relevant past state).

**2. Collapse Exploits**
- **2-D → 1-D Collapse** — Treat each row (or column) as a single "element" and run Family 1 techniques on the resulting sequence.
- **Tree → Path Collapse** — Many tree problems reduce to two path problems or to a diameter calculation.
- **Interval → Event Collapse** — Every range problem becomes a sorted list of +1 / –1 events (Sweep Line).

**3. Amortization Exploits**
- **Two-Pointer / Window Credit** — Each element enters and leaves the structure at most once → total $O(n)$ even if a single step looks expensive.
- **Monotonic Deque Credit** — Same credit argument; preferred over a heap for pure sliding-window extremes.
- **Union-Find Potential** — Path compression + union-by-rank makes the potential function so flat that operations are effectively $O(1)$.

**4. State-Design Exploits (Family 5 core)**
- **Minimal State Tuple** — Keep only the dimensions that affect future decisions.
- **Collision Guarantee** — Two different paths that reach the same state must have identical future options — otherwise the state is incomplete.
- **Bitmask as Coordinate** — When $n \le 20$, the subset itself becomes a compact integer coordinate in the state space.

**5. Embedding Exploits (most common real usage of Family 4)**
- Window + Monotonic Deque / Heap → Sliding Window Maximum / Minimum
- Graph + Heap → Dijkstra / Prim / A*
- Sweep Line + Heap → Skyline, online medians
- DFS + Trie → Word Search II style pruning

**6. Constraint-as-GPS Exploit**
When the interviewer adds a new constraint mid-problem, treat it as a deliberate currency shutdown pointing to the exact next link in the failure chain. Example: "Now the array can contain negatives" = Frame's assumption surface destroyed → move to Ledger.

## Runtime Safety Checklist (JS/TS)

Run this before writing a single line of code.

| #   | Check                                                                            | Why                                                             |
| --- | -------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 1   | No `.slice` / `.splice` / spread / `.filter().map()` inside loops → pure indices | Hidden $O(n)$ copy per call turns $O(n)$ into $O(n^2)$          |
| 2   | `map.get(x) ?? 0` after `.has(x)` — never `\|\| 0` when zero is valid            | `\|\|` treats `0` as falsy and silently substitutes the default |
| 3   | Numeric sort: `(a, b) => a - b`                                                  | `arr.sort()` with no comparator sorts lexicographically         |
| 4   | Recursion depth > ~10–15k → convert to explicit stack                            | JS call stack is finite and relatively small                    |
| 5   | Arbitrary heap deletion → lazy deletion with frequency map + skip stale on pop   | No native support for arbitrary removal from a heap             |
| 6   | Large $n$ + small value domain → prefer TypedArrays over `Map` for counts        | Lower memory, better cache behavior                             |
| 7   | Blind non-null assertion (`!`) on `Map.get` → guard with `.has()` first          | Runtime crash when the key is actually missing                  |

**Landmine Taxonomy (expanded reference)**

| Category         | Examples                                                  | Consequence                                                    |
| ---------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| Allocation       | `.slice()`, `.splice()`, spread, `.filter().map()` chains | Hidden $O(n^2)$ or heavy GC pressure                           |
| Coercion & Falsy | `map.get(x) \|\| 0`, truthy checks on counts              | Incorrect results when the value is 0                          |
| Sorting          | `arr.sort()` without comparator                           | Lexicographical order breaks numeric monotonicity              |
| Recursion        | Deep DFS / backtracking / top-down DP                     | Call-stack overflow                                            |
| TypeScript       | Blind `!` non-null assertion on `Map.get`                 | Runtime crash when key is missing                              |
| Memory           | Many large `Map`s on $n \geq 10^6$                        | Memory Limit Exceeded; prefer TypedArrays when domain is small |

**Core Idioms**
- Safe Map access: `.has()` + `?? 0`
- Numeric sort: `(a, b) => a - b`
- Grid directions: `[[-1,0],[1,0],[0,-1],[0,1]]` (add diagonals for 8-directional)
- Monotonic deque for window extremes
- Lazy deletion for heaps
- Bitmask representation of subsets ($n \leq 20$)
- Explicit stack or queue instead of deep recursion

## Self-Correction Triggers

Symptom-based debugging — what to suspect when something goes wrong mid-interview.

| Symptom                              | Likely Cause                                                     | Correction                                                   |
| ------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| Time Limit Exceeded                  | Residual nested work or missing state persistence                | Introduce Ledger / Frame, or reduce allocation               |
| Stack overflow                       | Excessive recursion depth                                        | Convert to iterative (explicit stack/queue, or bottom-up DP) |
| Wrong answer after sorting           | Missing numeric comparator, or lost original indices             | Add comparator; store original index alongside value         |
| `undefined` / `NaN` from Maps        | Missing `.has()` or falsy handling                               | Use `.has()` + `??`                                          |
| Passes small cases, fails large ones | Hidden quadratic behavior (usually allocation or repeated scans) | Eliminate intermediate arrays; single-pass state             |

## Complete Execution Mantra (Final Form)

When facing any problem:

1. **Topology** — what is the physical shape?
2. **Budget** — what asymptotic class is legal? (→ 04, §2)
3. **Algebra** — order? overlapping subproblems? dynamic updates?
4. **Mechanism** — which micro-system inside the routed family? (→ 05)
5. **Exploits** — duality, collapse, amortization, state design, embedding, constraint-as-GPS
6. **Failover** — if an assumption surface is violated, travel the exact chain or cross-family exit
7. **Safety** — run the JS/TS landmine checklist before writing code

**Operating principle:** constraints are signposts, not obstacles. When an interviewer adds a constraint, they are telling you which currency just got shut down — not trying to break your solution. *(For the fuller philosophical grounding of this idea, see 01 — Philosophy.)*
