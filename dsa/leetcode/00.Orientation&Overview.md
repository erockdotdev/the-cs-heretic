## What This Project Is

This is a dependency-driven framework for LeetCode-style algorithm problems, built around one central claim: **there aren't hundreds of techniques to memorize — there's a small set of physical data shapes, and a small set of resource trade-offs, and almost everything else is a predictable consequence of the two.**

Instead of learning "sliding window problems" and "graph problems" and "DP problems" as unrelated categories, this system organizes everything around two questions, asked in order:

1. **What is the physical shape of the input?** (a line, a sorted range, a network of nodes, a mutable stream, or a set of combinatorial choices)
2. **What resource is the interviewer restricting?** (time, space, order, or the ability to recover original information)

The shape tells you which of five families you're in. The restriction tells you which technique inside that family you're allowed to use. When a technique's assumptions get violated — negatives show up, extra memory gets banned, the array turns out to be rotated — you don't improvise. You follow a specific, pre-mapped chain to the next legal technique.

This isn't a claim that algorithms are *easy*. It's a claim that they're *structured* — and that structure, once internalized, replaces memorization with recognition.

## The Five Super-Families, in One Paragraph Each

**Family 1 — Linear Array Optimization.** Data is a line: an array, a string, a stream. The tools are Frame (sliding window), Ledger (prefix sum + hash map), and Vise (two pointers) — and they exist in a strict pecking order. Try Frame first; if negatives or non-monotonic data break it, move to Ledger; if you're banned from extra space, move to Vise; if you then need original indices back, you return to Ledger and pay for them.

**Family 2 — Sorted Search & Range Compression.** Data is sorted, or can be treated as intervals on a line. Binary search discards half the search space every step; sweep line collapses overlapping ranges into a single linear pass. The recurring trap: order exists, but naive code still scans everything — the family exists to stop you doing that.

**Family 3 — Hierarchical & Network State.** Data is nodes and edges — trees, graphs, grids. DFS and BFS are the two mechanical levers (depth vs. breadth), and Union-Find handles connectivity under repeated merges. This family builds directly on the "never recompute, never loop forever" discipline learned in Family 1.

**Family 4 — Dynamic Priority & Streaming.** Data is mutable or arrives over time, so re-sorting on every update is too expensive. Heaps give continuous access to the current min/max; tries exploit shared prefixes in strings. This family is unusual in that it's most often *embedded inside* the other four rather than being the primary structure of a problem — a heap inside a graph traversal (Dijkstra), a deque inside a sliding window.

**Family 5 — Exhaustive State-Space & Optimization.** The problem is a sequence of choices with an exponential number of futures. Greedy is extreme confidence (commit to the local best choice and never look back); Backtracking is brute-force exploration with pruning; Dynamic Programming is extreme humility (assume you can't predict the future, so remember every state that might matter). This family can sit on top of any topology from the other four.

## The Core Layer vs. the Family Subdirectories

This "Core" layer (the doc you're reading plus 01–05) is deliberately **topology-and-technique-agnostic at the surface level** — it's the map, the vocabulary, the math, and the operating protocol that apply *across* all five families.

Each Super-Family also has its own dedicated subdirectory with worked problems and family-specific depth. Core doesn't try to replace that — it's the layer you read *before* diving into a family's subdirectory, so that once you're there, you already know why the technique you're learning exists, what it will fail on, and where it hands off when it does.

If Core is the map of the terrain, the family subdirectories are the terrain itself.
