# L-01 — The Lattice Model

### 1. Universal Meta-Structure  
**The Constrained Directed State-Transition Lattice**

*A formal, standalone way of looking at the same territory Core (00–05) already covers practically. Terminology here is deliberately its own — see L-00 for why. This doc consolidates what was originally six-plus overlapping drafts of the same model into one pass.*

---

## 1. The Formal Model

$$L = (S, T, \Phi, C)$$

- **$S$ — State Space.** The set of all possible configurations of knowledge the algorithm can hold at any moment. Examples: current window bounds, a prefix-sum-plus-map snapshot, a node plus its visited set, a decision history, heap contents, a DP state tuple.
- **$T$ — Transition Relation.** The legal moves that take one state to another. Examples: expand/shrink a window, move a pointer, take a graph edge, insert/extract from a heap, choose a decision, merge two components, advance a sweep line.
- **$\Phi$ — Invariant / Potential Function.** The condition that decides whether a state is still valid, whether it can be pruned, whether two states are equivalent, and the amortized cost bound. This is the source of every correctness proof and every linear/near-linear amortized guarantee in the system.
- **$C$ — Currency Constraints.** The same four resource limits from 01 — Philosophy: Time, Space, Order, Integrity. These make regions of the lattice illegal or too expensive.

The claim: every concrete data structure, every Super-Family, and every problem is a particular geometric and algebraic specialization of this one object.

## 2. The Universal Meta-Algorithm

```typescript
function latticeReduction(initial: State, currencies: C): Answer {
  const ledger   = createCompressor();   // visited, prefix map, DP table, Union-Find, bitmask…
  const frontier = createFrontier();     // queue, stack, heap, two pointers, window, binary-search bounds…

  frontier.insert(initial);
  ledger.record(initial);

  while (!frontier.empty()) {
    const s = frontier.extract();        // pop / shift / extract-min / advance pointers / mid

    if (!Φ(s) || violates(currencies, s)) continue;   // 1. Invariant + currency check
    if (isGoal(s)) updateAnswer(s);                    // 2. Terminal / goal check

    for (const t of generateTransitions(s)) {          // 3. Generate candidate transitions
      if (algebraicallyDominated(t, Φ)) continue;       // 4. Algebraic pruning (the dominant speed-up)
      if (ledger.hasEquivalent(t)) {                     // 5. State compression
        ledger.merge(t);                                // DP hit, already visited, prefix already seen…
        continue;
      }
      ledger.record(t);
      frontier.insert(t);
    }
  }
  return extractAnswer();
}
```

What changes between problems is only the concrete shape of $S$ and $T$, the particular $\Phi$ (monotonicity, monoid, optimal substructure, heap order, etc.), which currencies are still legal, and the implementation of frontier and ledger. **The loop itself never changes.**

### Anatomy, in plain terms

| Component              | Role                                                                             | Concrete examples                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Frontier**           | The exploration engine — what still needs to be looked at                        | Two pointers (Sliding Window); a Queue (BFS); a Stack / call stack (Backtracking, DFS); active bounds `lo`/`hi` (Binary Search) |
| **Invariant ($\Phi$)** | The boundary gatekeeper — the rule that must hold for a state to be legal        | Window sum/frequency constraint still valid; node in bounds and reachable; `lo <= hi`                                           |
| **Ledger**             | The history/state compressor — how you avoid repeating work or losing your place | Hash map of past prefix sums; a `visited` set or distance map; a DP memoization table                                           |

## 3. How the Five Families Are Derived

The central claim of this model: the Five Super-Families are not five categories someone chose. They're the only five stable, efficient regions that appear when you vary the geometry of $S,T$ and the algebraic strength of $\Phi$ under realistic currency limits $C$.

| Lattice Geometry + Strongest Algebra                             | Forced Family                       | Why forced                                                                    |
| ---------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------- |
| Path graph + monoid / monotonic window validity                  | **Family 1 — Linear**               | Only window / prefix / two-pointer compression remains efficient              |
| Totally ordered line or interval endpoints + strict monotonicity | **Family 2 — Sorted / Ranges**      | Binary search or sweep become the cheapest pruning methods                    |
| Arbitrary graph (tree = acyclic case) + reachability             | **Family 3 — Network**              | Explicit traversal + visited / Union-Find required                            |
| Mutable / streaming elements + partial order                     | **Family 4 — Priority / Streaming** | Heap, monotonic deque, or trie are the minimal legal structures               |
| Exponential decision tree + optimal substructure or matroid      | **Family 5 — State-Space**          | Exhaustive search with compression (DP) or extremal pruning (greedy) required |

No sixth top-level family arises inside the domain.

### Per-family lattice parameters

*(For the full variant matrices and failure-driven chains in Core's own language, see 02 — Taxonomy and 05 — Micro-Systems. What follows is only the lattice-parameter view — why each family is forced, not the complete mechanism catalog.)*

**Family 1 — Linear.** $S$ = positions or windows on a path graph. $T$ = expansion/contraction of a contiguous segment or two-pointer movement. $\Phi$ = monoid structure (prefix sums work because addition is associative) or monotonic window validity. $C$ = nested loops are illegal; state must persist. Forced chain: monotonic validity holds → **Frame**; validity destroyed (negatives, arbitrary updates) → **Ledger**; Space forbidden → sort and destroy Integrity → **Vise**; indices required again → back to Ledger.

**Family 2 — Sorted / Ranges.** $S$ = positions on a totally ordered line, or active interval sets on a timeline. $T$ = jumping to midpoint, or processing sorted events. $\Phi$ = strict monotonicity of feasibility, or interval containment. $C$ = linear scan too slow, or naive interval cross-checks explode. Forced variants: exact target → Classic Binary Search; rotated → find pivot first; answer itself is the search space → Binary Search on Answer; overlapping ranges → Sweep Line.

**Family 3 — Network.** $S$ = nodes plus auxiliary state (visited, parent, distance, component). $T$ = edges of an explicit or implicit graph (a grid is a regular lattice graph). $\Phi$ = reachability, acyclicity, or connectivity. $C$ = cycles cause non-termination; exponential path enumeration is illegal. Forced chain: pure tree → DFS/BFS with parent only; cycles appear → add visited/coloring; unweighted shortest path → BFS; dynamic merges → Union-Find; weighted edges → currency forces exit to Family 4; count-all-paths or heavy constraints → exit to Family 5.

**Family 4 — Priority / Streaming.** $S$ = the current live multiset of elements (or string prefixes). $T$ = insertions, deletions, extract-min/max, or character extensions. $\Phi$ = heap order property or trie prefix-sharing. $C$ = full re-sort on every update is too expensive. Most common usage is embedding: window + monotonic deque (Sliding Window Maximum), graph + heap (Dijkstra/Prim), sweep + heap (Skyline).

**Family 5 — State-Space.** $S$ = partial decision sequences, subsets, or placements. $T$ = choosing the next decision. $\Phi$ = optimal substructure + overlapping subproblems, or matroid exchange property. $C$ = naive $O(b^d)$ expansion exceeds the time budget. Forced chain: matroid/exchange property holds → **Greedy**; property fails, $n$ small or all solutions needed → **Backtracking**; overlapping subproblems + larger $n$ → **DP**; $n \le 20$ + subsets → **Bitmask DP**.

### Cross-family movement is also forced

When the lattice parameters change mid-problem — a new currency shutdown, or a newly discovered algebraic property — the system is forced to move, not just permitted to:

- Linear path + need for order statistic under a window → embed Family 4 deque
- Graph + weights → embed Family 4 heap (Dijkstra)
- Any topology + combinatorial explosion → Family 5
- 2-D matrix that's really independent rows → collapse back to Family 1

These are not optional heuristics — under this model, they're the only remaining legal regions of the lattice once the prior region is exhausted.

## 4. The Whiteboard Derivation Protocol

When facing a problem you've never seen before, don't try to recall code from memory. Derive it by building the loop outward in four steps:

**Step 1 — Design the Ledger.** What past information do I need to make my next decision, and what can I throw away? Need past sums → frequency map or rolling accumulator. Need to avoid infinite loops → `visited` set. Need to avoid recomputing overlapping subproblems → memoization array/map.

**Step 2 — Initialize the Frontier.** What is my initial state of knowledge? Array → pointers at index 0. Graph → starting node pushed into a queue. Combinatorial problem → empty choice array or index 0.

**Step 3 — Write the universal loop structure** before any problem-specific logic:

```typescript
const ledger = new Map(); // or Set, or Array
const frontier = [initialState];

while (frontier.length > 0) {
    const curr = frontier.shift(); // or pop()
    if (!isValid(curr)) continue;              // Invariant check
    if (ledger.has(curr)) continue;             // State compression check
    ledger.set(curr, true);
    // Expand transitions...
}
```

**Step 4 — Inject the problem-specific logic.** Only now write the inner transition rules — how pointers increment, how graph neighbors get pushed, how DP choices branch. The structural skeleton already handles flow and memory safety, so this step is the only one that actually requires thinking about *this* problem.

## 5. Worked Example: The Full Stack

**Two Sum.** After stripping the narrative (see L-02 for that step in detail), the exposed lattice: a path graph, states = value-seen-so-far mapped to index.

- **Lattice parameters:** $\Phi$ = monoid-adjacent ("have I seen this value's complement"); $C$ = need $O(n)$ time and need Integrity (original indices), so Space is the currency to spend.
- **Forced family & mechanism:** Family 1 → Ledger (the currency profile — need Integrity, willing to pay Space — is exactly the Ledger's assumption surface).
- **Frontier/Ledger instantiation:** Frontier = a single left-to-right scan; Ledger = `Map<value, index>`.

```typescript
function twoSum(nums: number[], target: number): number[] {
  const ledger = new Map<number, number>(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (ledger.has(need)) return [ledger.get(need)!, i];
    ledger.set(nums[i], i);
  }
  return [];
}
```

The value of the lattice framing here isn't the code — the code is identical to what you'd write from Core alone. It's that you now know *why* it's Ledger rather than Vise, and exactly which currency shutdown would force the switch (if the interviewer demands $O(1)$ space, Integrity is what you'd have to give up next).

## 6. Lattice Mechanics for Hard Problems

*This section has no direct Core equivalent — it's the most substantively new material in this track.*

Hard problems almost never live in a clean, single-region lattice. They force you into a more complex region of $L=(S,T,\Phi,C)$ where at least one of the following is true: the natural geometry is higher-dimensional or implicit; $\Phi$ is weak or expensive to maintain; multiple currencies are simultaneously tight; or useful compression only appears after a non-obvious rewrite.

**1. State explosion and aggressive compression.** The raw state space $|S|$ is usually exponential. The meta-algorithm survives only if $\Phi$ supplies a powerful equivalence relation collapsing many histories into one. Interval DP (state = subarray $[l..r]$), Tree DP (state = node + local configuration), Bitmask DP ($n \le 20$, state = subset), and Digit/profile DP all work this way — $\Phi$ declares two partial solutions equivalent when their future options are identical, and the ledger stores one representative per class.

**2. Multi-dimensional or implicit lattices that must be collapsed.** A 2-D or higher appearance is often expensive to treat directly; the winning move is a forced dimensional collapse into a cheaper region. Largest Rectangle in Histogram: treat each row as a 1-D histogram → Family 1 monotonic stack. Cherry Pickup-style two-agent grid paths: a 4-D state compresses via simultaneous movement or diagonal-line reduction. Matrix Chain / Burst Balloons: the interval lattice supplies $\Phi$ directly via optimal substructure on intervals.

**3. Partial-order maintenance under tight time (Family 4 embeddings).** When continuous order statistics are needed on top of a linear or graph topology, full sorting is illegal, so a heap or monotonic deque becomes part of the frontier or ledger. Sliding Window Maximum/Median embeds a monotonic deque or two heaps into a Family 1 lattice. Skyline embeds a max-heap into a Family 2 timeline. Dijkstra/Prim on dense graphs embeds a priority queue into a Family 3 lattice because weights destroy plain BFS.

**4. Weak or expensive invariants → heavy pruning.** When $\Phi$ alone can't prune early enough, strengthen it with dominance rules, admissible heuristics, or problem-specific bounds. N-Queens/Sudoku add forward-checking or exact-cover techniques. Branch-and-bound extends $\Phi$ with a lower/upper bound that prunes whole subtrees. A* strengthens $\Phi$ with an admissible heuristic that still guarantees optimality. The loop itself doesn't change — only `algebraicallyDominated(t, Φ)` gets more sophisticated, and that's what moves a solution from TLE to accepted.

**5. Simultaneous currency pressure.** Hard problems often shut down two currencies at once, leaving a narrow legal region: need original indices *and* near-linear time → can't sort, must pay Space instead. Need $O(1)$ space *and* handle negatives → Frame dies, and Vise-after-sort may also be illegal if indices matter, sometimes forcing a two-pass or closed-form solution instead. Online/streaming *and* order statistics → a dynamic partial-order structure (Family 4) replaces a static sort.

**6. Composite lattices (cross-family by necessity).** The hardest problems are rarely pure members of one family — their lattice is a product of two regions. Graph + Decision (shortest path with exactly $k$ edges — DP where state = node + extra parameter). Interval + Decision (Burst Balloons, Matrix Chain). Path + Partial Order (sliding window extremes, stock problems with cooldown). Tree + Decision (Tree DP — house robber on a tree, diameter with weights).

**7. Practical diagnostic sequence for Hard-rated problems**

1. Strip the narrative harder — it's usually thicker on Hard problems.
2. Estimate the raw lattice size — if $|S|$ looks exponential, compression or collapse is mandatory.
3. Search for collapse opportunities: 2-D → 1-D, tree → path, intervals → events.
4. Identify required order statistics or dynamic updates — plan the Family 4 embedding early if present.
5. Design the minimal state tuple first (especially for DP), applying the Collision Guarantee: two histories reaching the same state must have identical future options.
6. Write $\Phi$ explicitly before coding. If it's weak, strengthen it with bounds or dominance.
7. Only then instantiate frontier and ledger and write the loop.
8. Audit every currency restriction and confirm the chosen region satisfies all of them.

| Mechanic                          | What it does to the lattice                            | Typical trigger                                |
| --------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| Aggressive state compression      | Collapses exponential histories into polynomial states | Overlapping subproblems, $n \le 20$ subsets    |
| Dimensional / structural collapse | Rewrites geometry into a cheaper region                | Matrices, histograms, trees-as-paths           |
| Partial-order embedding           | Adds a heap/deque/trie to the frontier or ledger       | Window extremes, weighted graphs, skyline      |
| Strengthened pruning              | Makes `algebraicallyDominated` far more powerful       | Constraint satisfaction, branch-and-bound      |
| Multi-currency pressure           | Forces narrow legal regions and precise trade-offs     | $O(1)$ space + negatives, online + order stats |
| Composite lattices                | Product of two families                                | Graph DP, Tree DP, Interval DP                 |

Hard problems don't require a different meta-algorithm. They require a deeper reading of $S, T, \Phi, C$ and more skillful rewriting of the lattice until a region appears where the ordinary meta-algorithm becomes efficient again.

## 7. Absolute Clarity Statement

Inside the domain of LeetCode-style algorithmic problems:

- Every problem is an instance of the Constrained Directed State-Transition Lattice $L=(S,T,\Phi,C)$.
- The geometry of $S,T$ and the algebraic strength of $\Phi$ under the currency limits $C$ force membership in one (or a cross-product) of the Five Super-Families.
- The same parameters force the precise mechanism and the legal failover path.
- Change the geometry → the family is forced. Change the algebraic strength of $\Phi$ → the mechanism inside the family is forced. Shut down a currency → the failure-driven transition is forced.

Once a problem is reduced to its lattice parameters, membership in a family, choice of mechanism, and legal failover path become mathematical consequences rather than design decisions — the families and the individual solutions are *derived* from the meta-structure, not arbitrary categories imposed on top of it.
